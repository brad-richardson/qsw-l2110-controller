# Peer-side LACP controls — 2026-09-06

**There are useful peer-side experiments left, but current captures do not show malformed Linux LACP. A generic “turn on Fast” workaround was already tried on Firewalla and failed to repair port 4.** All new work below is proposed for the isolated, unaddressed USB bench. Nothing was applied, and Firewalla settings remain untouched.

## What the actual healthy/failing captures show

Compared successful sweep trial 006 (1+7) in `backups/usb-sweep-20260906T183251Z` against the full 360.030-second failing repeat `backups/usb-sweep-20260906T192611Z`.

- Every LACP frame inside both trial windows has captured/original length **124 bytes**, no VLAN tag, EtherType `0x8809`, subtype/version `1/1`, expected actor/partner TLVs, collector TLV type3/length16, and identical zero-filled remaining collector/terminator/reserved area. No frame-format difference in those fields explains the reversal. This is a capture-level comparison, not exhaustive formal conformance certification or evidence about wire FCS.
- All frames use destination `01:80:c2:00:00:02`. Linux Ethernet sources remain permanent NIC MACs `5c:85:7e:38:d8:d1` and `a0:ce:c8:59:74:22`, while actor identity is shared across members and changes between runs (`02:17:fa:21:54:71` → `02:3f:6c:3a:ff:a7`). - Linux actor key9, system priority65535, port priority255, member IDs1/2 are identical between runs. QNAP key1, system priority32768, port priority128 and port IDs1/7 are also identical. Healthy steady state has61/61: both active, aggregation/synchronization/collecting/distributing, long timeout, no defaulted/expired flags.
- In the failed repeat, QNAP7 sends **12 PDUs**, every one actor69 with completely zero partner fields; Linux records **28 outgoing PDUs** on that member. Linux eventually advertises13/69, showing it receives and identifies QNAP7 but QNAP never acknowledges Linux. Port1 succeeds throughout. Linux source explicitly puts each member's **permanent MAC** into the Ethernet source and independently supplies actor information. Its receive path sets need-to-transmit when the peer's partner information disagrees; its periodic state responds to the partner timeout flag. Thus the source/actor split and additional responses have a direct implementation explanation. This is upstream source, not proof that the running binary is identical. ## Controls, ranked by expected information

1. **Fixed identity and startup timing, then good-port priming.** Highest value and least novelty: reproduce sweep-style LAG apply followed immediately by bond start while keeping actor, NIC assignment, member order, and timers fixed. Then test1+7→1+3→1+7 with only the second cable moving and the actor unchanged. The old2+3 pair cannot literally be prerequisite because it occurred *after*1+7 passed; prior negotiation of the second actor-port on2 or3 remains untested. Hold the final1+7 ≥360seconds. Add an explicit actor option to the harness; a new invocation currently randomizes it.

2. **Actor identity A/B/A without changing Ethernet source.** Keep QNAP configuration and cable placement fixed, standardize the rebuild/down duration, compare old sweep actor versus current repeat actor and back again. Because Linux LACP Ethernet sources remain permanent per-member MACs, this chiefly tests protocol-system identity and associated internal state, rather than ordinary source-MAC learning. A result may identify a workaround worth passing to Firewalla engineering, but must reproduce across repeated runs and boot before recommending a persistent identity change.

3. **Separate member identity from physical port and startup order.** Reverse Linux member insertion order with both cables fixed; this swaps advertised actor-port1/2 while keeping NIC-to-QNAP mapping fixed. Separately compare software member7-first versus1-first, recording actual carrier and PDU timing. Then physical NIC/cable swaps form a third, separate control. Historical Firewalla cable/member swaps and port4-first bring-up already failed to rescue3+4, so the hypothesis is narrower than “wrong cable order.” No such controlled order reversal has been recorded for successful-versus-failing USB1+7.

4. **System priority control.** Compare peer priority65535 against a value below QNAP32768, e.g.16384, keeping actor and all other settings fixed. This tests whether QNAP's selection/control path behaves differently with a different peer priority. It is a compatibility hypothesis, not correction of an invalid baseline. QNAP's zero-partner reports suggest a problem earlier than ordinary selection, so rank below history/identity controls.

5. **Active versus passive.** Keep QNAP active (its observed activity bit is set) and make the USB peer passive for one bounded trial. This tests whether switch-initiated negotiation differs from the current both-active exchange. It may reduce unsolicited Linux periodic traffic but still permits protocol responses; it is not a way to turn LACP off. Keep actor and startup timing fixed. This control is untested in the local records.

6. **Directional cadence, only if needed after the above.** A complete USB rate matrix (QNAPLong/Short × LinuxSlow/Fast) is untested on1+7, but the production3+4 experiment already rules out claiming that the obvious Fast/Fast choice was never tried. Treat cadence as a diagnostic probe, not the leading fix. Explicitly measure both directions' actual spacing and timeout bits; changing Linux's request is not synonymous with directly forcing Linux's transmission interval.

Linux exposes `ad_actor_system`, `ad_actor_sys_prio`, `ad_user_port_key`, `lacp_active`, and `lacp_rate`; its documented rate setting requests the **partner's** cadence. Its key reserves lower bits for negotiated speed/duplex and upper ten bits for user choice. These options should be applied in the isolated peer's creation path and read back; availability and live-update restrictions must be checked against the running kernel. [Linux bonding documentation](https://docs.kernel.org/networking/bonding.html)

## If standard peer controls do not discriminate

**Open vSwitch is a useful independent LACP implementation**, with explicit system ID/priority, per-member port IDs/priorities/aggregation key, active/passive mode, and Slow/Fast request controls. It permits matching Linux's advertised identity while varying one field or the state-machine implementation. Keep its bridge unaddressed and disconnected from host management; use no fallback forwarding when judging LACP. The setup adds more moving parts, so do it after the small Linux controls rather than as the first step. [OVS database schema: LACP options](https://www.openvswitch.org/support/dist-docs/ovs-vswitchd.conf.db.5.html)

A final specialized probe could use a **single bounded userspace LACP responder** in place of the kernel bond, with a working-port positive control. Preserve the same actor/key/port fields and vary one field or timing dimension: stable one-second transmission while retaining a Long receive-timeout advertisement, reply immediately versus a fixed short delay, or source MAC identical to actor versus ordinary per-member source. Record whether QNAP ever fills its partner TLV and how quickly. Keep its state truthful; hard-coding synchronized/collecting flags is not evidence of successful LACP. Do not run it alongside the kernel LACP sender or blindly replay packets from a different identity/state. Source-MAC equality tests are lower priority because the existing split is normal Linux behavior and succeeds on the same equipment elsewhere.

This would be an experiment construction rather than a standard supported Firewalla setting. If a repeatable difference appears, the engineering handoff should contain the minimal pair of emitted frame sequences and QNAP responses. A Linux TX counter or PCAP alone remains insufficient to prove that every frame reached the switch; receive-side mirroring or a suitable independent capture is stronger where available.

## Already-tested cadence history — do not lose this distinction

`docs/lacp-review-20260905.md:139` describes the first live Firewalla rate write failing with EBUSY: **that attempt did not test Fast**. But the later authorized down/change/up experiment at20:30–20:35UTC did successfully set Fast. Working port3 then saw295 QNAP PDUs in aboutfive minutes; failing port4 saw onlyten, all actor71 with zero partner. FirewallaFast requested faster QNAP sends, but the failing port continued approximately30-second sends, consistent with not learning/retaining that peer's request. Returning Slow did not restore internet until the user's reset. Do not repeat that production outage as a routine knob test.

`docs/macbook-timeout-results-20260905.md` records a distinct Mac issue: Short caused repeated expiration, Long stayed clean449seconds, return to Short reproduced it. That supports peer-specific timer interaction but is not evidence that the current Linux1+7 missing-partner failure has the same cause.

## What is unlikely to fix this specific negotiation failure

Transmit hash policy, `min_links`, ordinary IP settings, MTU/jumbo size, TCP offload, and bulk throughput tuning do not directly address QNAP reporting a zero LACP partner on one member. They may affect forwarding or visibility, and arbitrary changes would add confounders. The initial ASIX native speed/duplex/driver failures were real peer problems, but the two-r8152 positive controls and identical good/bad frame structure do not currently identify an equivalent issue in the replacement peer.

For Firewalla engineering, a valuable deliverable is a repeatable **one-variable peer control**, with exact Linux/kernel/driver versions, immutable actor identity, QNAP pair/group/VLAN/firmware, startup timing, native states, both directions' PCAPs, and one known-good control. It is reasonable to seek a peer workaround without asserting the original fault is Firewalla's; the independent Linux peer has reproduced the same class of QNAP-port failure.
